Where we were

Quality checks existed, but only as manual commands

TypeFeud already had tests, TypeScript checks, content validation, and a production build. The web app also had Next.js lint rules. What it did not have was an automatic gate that ran those contracts on every push and pull request, or a common lint and formatting contract for the server and shared packages.

That meant a developer could merge code without GitHub proving that the full monorepo still passed. It also meant four of the five workspaces had no lint command for Turbo to invoke.

Why this work matters: the repository already depended on several independent quality checks; CI turns them from a remembered local routine into one repeatable merge contract.

Architecture

The verification flow

A push or pull request starts one read-only verify job. The job installs the repository's pinned pnpm and Node versions, then runs five named checks in sequence. The named steps make a failure visible without opening raw logs to discover which contract broke.

push / pull_request │ ▼ ┌───────────────────────────────┐ │ CI / verify │ │ ubuntu-latest · 15 min limit │ │ contents: read │ └──────────────┬────────────────┘ │ ▼ checkout → pnpm + Node 22 │ ┌──────────┴──────────┐ ▼ ▼ pnpm lint exact lockfile required │ pnpm store cached ├─ Turbo ESLint: 5 workspaces └─ Prettier repository check │ ▼ pnpm test │ ▼ pnpm typecheck │ ▼ validate content pools │ ▼ pnpm build │ ▼ one green merge signal
Why one job with separate steps: all checks share one installation, while the GitHub UI still identifies lint, test, typecheck, content, or build as the exact point of failure.
Continuous integration

The GitHub Actions job is intentionally small and strict

.github/workflows/ci.yml The workflow reacts to both push and pull_request. It grants only read access to repository contents and stops after 15 minutes instead of allowing a stuck build to run indefinitely.

Runtime and dependency reproducibility

  • actions/checkout@v7 checks out the exact revision being verified.
  • pnpm/setup@v2 reads pnpm@11.18.0 from the root package manifest.
  • Node 22 matches the repository's declared engine.
  • require-lockfile: true prevents CI from silently resolving a new dependency graph.
  • The pnpm store is cached to avoid redownloading unchanged dependencies.
  • Next.js and Turbo telemetry are disabled in the CI environment.

Stale-run cancellation

The concurrency key groups runs by workflow and ref. When another commit arrives on the same branch or pull request, the older run is cancelled and the newest revision becomes the only result that matters.

Tradeoff accepted: the checks run sequentially in one job rather than as parallel jobs. This reuses one setup and keeps the contract easy to read, at the cost of less parallel speed.
Monorepo coverage

Lint now reaches every workspace

The root command is now turbo run lint && pnpm format:check. Turbo first discovers and runs the lint task owned by each workspace. Only after all workspace lint tasks succeed does Prettier check the wider repository.

Why the web app keeps its own config: Next's Core Web Vitals, React, accessibility, and App Router rules are browser-specific. The shared config covers plain TypeScript without weakening those checks.

Turbo's lint task now depends on ^lint, so dependency packages are checked before packages that consume them. Generated dist, .next, .turbo, and node_modules directories are ignored by the shared config.

Consistent source

Prettier establishes a clean baseline

.prettierrc.json Formatting now matches the repository's documented style: two spaces, double quotes, semicolons, trailing commas, and a 120-column width. Developers can use pnpm format to apply it or pnpm format:check to verify it without writing files.

The initial run normalized 37 existing source and configuration files. Those edits change wrapping and layout, not game behavior. Keeping the baseline in the same change means the first CI run does not fail immediately on pre-existing formatting differences.

Tradeoff accepted: the first tooling change has a broad diff. After this one-time baseline, future formatting diffs should be small and attributable to the feature being edited.
Why generated and authored documents are excluded: design, plan, and review HTML files are deliberate artifacts, while build and cache directories are generated. Reformatting either would create noise without improving production TypeScript.
Non-obvious calls

Version choices favor a warning-free install

ESLint remains on major version 9

ESLint 10 is available, but plugins pulled in by eslint-config-next@16.3.0 still declare ESLint 9 as their supported maximum. The repository therefore pins ESLint ^9.39.5 rather than forcing the newer major and accepting peer-dependency warnings on every install.

Why: a clean dependency contract is more valuable than adopting a new lint major before the framework's own plugin set supports it.

The local pnpm cache is ignored

Repairing the local pnpm installation created .pnpm-store/ inside the repository. It is now listed in .gitignore alongside node_modules, preventing machine-local cache data from entering commits.

Out of scope and final gate

What remains before Issue #1 is truly closed

Commit and push: all CI and tooling files currently exist only as working-tree changes on main. Until they are committed and pushed, GitHub cannot discover the workflow.
First hosted run: after the push, confirm that the first CI / verify run succeeds on GitHub. Local success proves the commands; the hosted run proves the workflow permissions, action setup, and clean-machine installation path.
ESLint 10: reconsider the major upgrade when Next.js and its bundled lint plugins advertise compatible peer ranges. It is not required for this CI contract.

For the reviewer

Reviewer's checklist

  • Confirm the workflow has read-only permissions and runs on both pushes and pull requests.
  • Confirm Node 22 and pnpm@11.18.0 match the repository manifest.
  • Check that lockfile enforcement is active and the pnpm store—not node_modules—is cached.
  • Verify all five quality contracts appear as distinct GitHub Actions steps.
  • Confirm all five workspaces participate in Turbo linting and the web app retains its Next.js rules.
  • Spot-check the broad source diff to ensure it is formatting-only, especially the larger session and hook files.
  • After push, require the first CI / verify run to be green before closing Issue #1.
Mental model for this review: this change does not alter TypeFeud's game rules. It turns the repository's existing quality expectations into an automatic, reproducible gate and makes lint/format coverage consistent across the monorepo.
