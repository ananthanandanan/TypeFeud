Key code

Three places where the obvious implementation is the wrong one.

packages/game/src/engine.ts — the lock-in rule
/**
 * Lock a line in. SPEC §2.3 — the first keystroke matching an option's first
 * character chooses that line, and counts as its first character.
 *
 * Matching is case-insensitive: a missed shift must not leave the keyboard
 * dead. The keystroke is then applied verbatim, so the case slip lands as an
 * ordinary error the player can backspace over (invariant 6).
 *
 * Ties are broken in tier order (jab, combo, haymaker). The dealer avoids
 * dealing a tie at all, so this is the floor, not the mechanic.
 */
export function lockIn(state: RoundState, ev: KeyEvent): RoundState {
  const slot = ev.slot ?? 0;
  const player = state.players[slot];
  if (player.progress || ev.key.length !== 1) return state;

  const chosen = player.options.find(
    (option) => option.text[0]?.toLowerCase() === ev.key.toLowerCase(),
  );
  if (!chosen) return state;

  const locked = withProgress(state, slot, createLineProgress(chosen.id));
  return applyKeystroke(locked, ev);
}
packages/content/src/deal.ts — dealing three that cannot collide
/**
 * One line per tier. Distinct first characters where the pool allows it, so
 * the lock-in tie-break in `lockIn` stays theoretical rather than a coin flip
 * the player cannot see coming.
 *
 * `rng` is a parameter, not Math.random: T-06 (#6) drops a seeded PRNG in here
 * and this file does not change. The `seen` filter is the same shape as the
 * eventual no-repeat ring buffer (SPEC §3.6), applied to one match for now.
 */
export function dealThree(
  round: RoundName,
  seen: readonly string[],
  rng: () => number,
): [Line, Line, Line] {
  const taken = new Set<string>();

  return TIERS.map((tier) => {
    const pool = linesFor({ round, tier }).filter((l) => !seen.includes(l.id));
    const fresh = pool.length ? pool : linesFor({ round, tier }); // pool exhausted
    const distinct = fresh.filter((l) => !taken.has(first(l)));
    const from = distinct.length ? distinct : fresh;

    const line = from[Math.floor(rng() * from.length)]!;
    taken.add(first(line));
    return toLine(line);
  }) as [Line, Line, Line];
}
apps/web/src/components/typing-stage.tsx — resolve once, then deal
// resolveLine deliberately leaves the finished line standing so the surface
// does not blank during the impact beat — the `resolved` ref is what keeps it
// from charging twice. The deal is the thing that actually clears progress,
// and it is the player's beat to take, not a timer's: enter deals.
useEffect(() => {
  if (!complete || resolved.current) return;
  resolved.current = true;
  const { state: after, outcome: landed } = resolveLine(state, { now: lastKeyAt }, tuning);
  setState(after);
  setOutcome(landed);
}, [complete, state, setState, lastKeyAt, tuning]);

const deal = useCallback(() => {
  setState((current) => {
    const you = current.players[0];
    return dealOptions(current, 0, dealThree(current.round, you.seenLineIds, Math.random));
  });
}, []);
06

Future scope

Four assumptions I made rather than come back and ask, and three things that are deliberately somebody else's issue.

Assumption · two options can share a first character

SPEC §2.3 does not say what happens, and with the pool as it stands it happens often — three of the six debate lines start with "Y". The plan solves it twice: the dealer prefers three distinct first characters, and lockIn falls back to tier order when the pool cannot supply them. The alternative — letting the player disambiguate with a second keystroke — is a much bigger mechanic and would slow the fastest players down, which is exactly backwards.

Decide with · the #12 tuning pass · revisit if the fallback ever fires in play

Assumption · lock-in is case-insensitive, typing is not

Typing lowercase w at WHAT locks the line in and immediately marks one error, repairable with backspace. The strict alternative ignores the keystroke entirely, which reads as a broken keyboard at the exact moment the round clock is running. "Errors never block" (invariant 6) points the same way.

Decide with · hand-check in slice 3 · cheap to flip

Assumption · the player reads the line twice

The canvas puts the full line in the 15px card and again at 32px in the surface once locked. That is a double read under time pressure and it may cost more than the choice is worth. I am building the settled design rather than improvising against it; if it reads badly by hand, the fix is a canvas change (truncate the card to its first clause) and not a code change.

Decide with · the design pass · would become issue #17

Assumption · enter deals the next triple

Today enter advances a line; the same key now deals three. The alternative is dealing automatically once the impact beat finishes, which is what #5 will want when the round clock is real. Keeping it manual for one more issue means the dev shortcuts stay unchanged and there is no animation-timed state transition to debug on top of a new mechanic.

Decide with · #5 · the round clock replaces it

Deferred · seeded selection and the no-repeat ring buffer

dealThree takes an rng and the caller passes Math.random. No-repeat is enforced within a match through seenLineIds, which is already on PlayerState, but the cross-match localStorage ring buffer of SPEC §3.6 is #6's work, and so is seeding. The parameter is here so that lands as a one-line change.

Decide with · nothing · issue #6 owns it

Deferred · the pool is six debate lines deep

Two lines per tier means the second deal of a match is nearly forced and the third has nothing unseen to offer, which is why the dealer falls back to repeating rather than dealing an empty slot. It makes the mechanic hard to judge honestly by hand. #11 writes the arenas; until then a "does the choice work" verdict is provisional.

Decide with · #11 · content, not code

Open · does anyone ever pick anything but the safe line?

SPEC §9's named failure mode. This issue cannot answer it — the damage numbers that make a haymaker worth the risk are #12's to tune, and there is no opponent pressure until #7. What this issue owes the question is that the choice is legible in the first place: three cards, three damage numbers, one keystroke. The handoff doc records a first impression, nothing stronger.
