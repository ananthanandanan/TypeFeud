01

Milestones

Build the shared opponent-progress path first, then place a deterministic canned source behind it and connect that source to the existing match lifecycle.

Slice 1

Accept opponent progress in the engine

Add a pure progress-snapshot transition for {lineId, charIndex, errors}. It selects only a currently offered line, keeps the first-seen start time, rejects impossible snapshots, and resolves a completed line once through the existing damage path. As built: a snapshot that moves charIndex backwards is not rejected — that is a backspace, it is indistinguishable from a stale packet, and invariant 6 says the repair is the real one. Ordering stays the transport's job. Snapshot-built progress carries typedChars: [] — the wire shape has no keys, so it cannot satisfy the typedChars.length === charIndex contract in types.ts. That is safe because resolveLine reads only charIndex, wrongIndices.length and startedAt, and nothing renders opponent characters — both facts are stated in the type and asserted in the tests.

Slice 2

Build the canned ghost source

Store a small set of normalized human timing traces. Choose an offered line deterministically, map the trace to its length, and add light seeded jitter. The result is a timed list of protocol-shaped progress snapshots, not synthetic key events.

Slice 3

Give the opponent its own round-scoped view state

MatchState holds lineOutcome, lastKeyAt and generation for slot 0 only, and session.ts raises line.resolved behind an input.slot === 0 guard. Mirror all three for the opponent before anything tries to schedule or display a ghost line — the impact-beat timer and the activity strip both read them, and neither can be built until they exist.

Slice 4

Drive every round under ?bot=1

Schedule one next ghost event at a time and feed it into advanceSession. The existing impact-beat effect cannot be reused: it dispatches a literal { slot: 0 } deal and is keyed on slot-0 lineOutcome and lastKeyAt. Add a parallel effect reading the opponent state from slice 3, then deal slot 1 and rebuild the schedule when the round or deal generation changes. Phase and generation guards make stale timers harmless.

03

Mockups

The only new visual is a restrained opponent activity strip. It confirms the ghost is typing while preserving the player’s typing panel as the main focus.

Why a strip and not a racer

TypeRacer answers “where is my opponent” with a car whose position is the progress. TypeFeud’s equivalent is the opponent’s stick figure, and it answers a different question: progress crossing a threshold plays a punch, and the thing that moves along the track is HP, not a position marker (SPEC §4.3, invariant 4 — derive animation from progress, never send animation events). Position on screen is already spoken for: you are always left, the opponent always right, which is rule 1 of the design system.

So the figure carries presence and the HP bar carries the race. Neither exists yet in motion — the figure states are Milestone 5 — which leaves this task with no continuous signal that the ghost is alive between hits. The strip fills exactly that hole. It is a legible stand-in, not a permanent fixture, and it is the one piece of this task the art milestone is free to delete.

Future scope

This task creates a credible fixed-skill development opponent and the replacement boundary. Matchmaking and skill adaptation remain later work.

Adaptive ghost skill

The launch bot should match the player’s recent WPM. Task #7 has no user-performance store yet, so it ships one moderate canned profile. The results/statistics task can add recent WPM and select among slow, medium and fast profiles without changing the stream consumer.
